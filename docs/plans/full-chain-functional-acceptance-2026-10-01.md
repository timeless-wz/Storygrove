# 全功能链路、存储连接与功能完整性验收方案

日期：2026-10-01。勘察基线：`b1cf592` 加当前工作树的未提交修改与新增文件。

**状态：测试设计已完成，本文不是验收通过报告。** 本轮只读取源码和测试配置、编写方案，没有运行全量测试、修改应用代码或操作小说项目数据库。执行时必须重新记录 HEAD、完整工作树差异及环境版本，不能把当前未提交功能遗漏在验收之外。

## 1. 要回答的三个问题

| 问题 | 验收方法 | 通过证据 |
| --- | --- | --- |
| 功能链路是否正确 | 从真实入口操作，追踪 store/service/workflow → preload → IPC controller → repository/service → 返回与界面刷新 | 实际参数、项目会话、提交收据、界面结果与下游读取一致 |
| 存储位置是否连通且正确 | 记录实际绝对路径；写入独特测试内容；从真实数据库/文件/向量库独立回读；退出后重新打开 | 持久化内容、所属项目、版本/哈希、引用一致；没有写到另一项目或全局目录 |
| 功能是否完善 | 按功能逐项验证成功、编辑、保存、取消、失败、恢复、重开、联动；只读功能验证读取与边界 | 必需场景全部完成；明确列出缺项、实现缺陷、环境阻塞、待人工评估项 |

统一证据链：

```text
真实用户入口
  → 输入与项目/会话身份
  → 前端服务或工作流
  → preload 与真实 IPC
  → 主进程处理器
  → 正确的数据库、文件或索引
  → 返回结果与当前界面刷新
  → 退出应用、重新启动、重新读取
  → 关联功能读取同一数据
```

“提示保存成功”“界面上出现卡片”“存在测试文件”只能作为部分证据。任何可持久化功能都必须有独立落盘回读。索引、剧情树、实体稿等派生数据还需与其事实源核对。

## 2. 范围与功能清单规则

主范围是当前桌面应用，包括新加入的蓝图 v2、世界工作台和修炼设置。独立 DeepSeek Harness 插件作为附加范围单独报告，它使用自己的工作区存储，不应与桌面项目混验。

执行前从以下四处交叉登记：

1. `src/App.tsx`、顶栏、侧栏、右侧参考栏、编辑器分支、设置页与上下文菜单里的所有用户入口。
2. `src/services/workflows/` 和 `src/services/agent/tools/` 的工作流与工具入口。
3. `src/shared/ipc-channels.ts`、`src/shared/phase3-8.ts`、`electron/preload.ts` 与实际 controller 注册。
4. SQLite schema、repository、项目文件写入服务与全局配置服务。

建立“入口 → 功能 → 实际调用 → 事实源 → 下游消费者 → 测试用例”的清单。IPC/表不要求逐一对应独立菜单，但必须标记为用户功能、内部支撑、兼容迁移或明确废弃；无法归属的入口/处理器/表必须列为待查，不能默认忽略。清单中的功能都要有用例和执行状态，才可以报告全功能覆盖。

源码扫描用于找遗漏，行为执行用于证明正确。覆盖率百分比不能替代业务链路验收。

## 3. 测试环境与固定数据

每次运行新建一个独立根目录，例如 `<测试根>/<runId>/`，其中包括：

```text
global-home/       测试全局设置，使用 AI_NOVEL_VELA_HOME 注入
electron-profile/ 测试 Electron 用户数据目录，单独隔离 localStorage
project-a/        主要验收项目
project-b/        隔离检查项目
legacy-project/   固定旧版本样本的副本
source-fixtures/  合成外部资料，按只读来源使用
export/           授权导出目标
backup/           备份目标
restored-project/ 从备份恢复的独立目标
evidence/         日志、截图、结构化结果和回读摘要
```

全局 home 与 Electron profile 必须同时隔离；只覆盖 `AI_NOVEL_VELA_HOME` 不足以隔离主题和灵感便签等 localStorage。Electron profile 隔离须由测试启动器在启动时设置，并用实际运行路径回读确认。

数据集要求：

- 项目 A/B 使用不同的唯一标记；同章号、同角色名、同世界名，用来发现串项目。
- A 至少两卷四章，每章两个草稿版本；其中一个草稿明确绑定蓝图，一个未绑定；章号故意不连续，避免代码依赖数组位置。
- 蓝图包含 v1 与 v2；v2 使用 `test/fixtures/blueprint-v2/chapter-01.md`，另加缺节、自由块、嵌套列表和特殊字符样本。
- 角色包含作者确认值、定稿派生值、候选值；世界包含两个世界、地图、势力、规则、宝物、门户、位置和轨迹。
- 资料包含 confirmed/candidate/deprecated 状态、缺失文件、变化文件、中文/空格文件名、非法 UTF-8、重复章号和损坏文件。
- 正文包括中文、英文、Markdown 标记、引号、换行、可定位引文和独特内容标记。
- 使用新的全局配置和模型 fixture；报告不输出密钥或真实小说正文。

固定期望数据由测试样本提供，不能直接调用被测函数生成期望结果。外部来源在测试前后计算哈希，证明导入/扫描没有修改来源。`D:\Desktop\小说` 不用作可写测试目录。旧项目迁移与故障注入只操作样本副本。

## 4. 存储连接检查表

以下路径来自当前源码；执行时记录应用实际解析出来的绝对路径，而不是只对照字符串。

| 数据 | 当前存储/事实源 | 需要核对的连接 |
| --- | --- | --- |

| 定稿与实体稿 | `finalization_outbox` 等事务数据；项目根目录章节 `.txt` | SQLite 为事实源；实体稿内容与冻结哈希一致；发布失败可重试 |

| 地图与世界 | `world_maps/nodes/edges`、`world_*` 表；`.vela/world-maps/<map-id>/` | 图片元数据与文件连接；人物/事件/世界引用正确；兼容迁移无重复 |
| 修炼体系 | `cultivation_meta/realms/levels` 与角色修炼引用 | 保存 revision、等级 ID、角色引用；删除/重排后的合法性 |
| 创作资料中枢 | `workspace_sources`、批准快照、候选、规则、上下文快照等 | 外部来源只读；批准版本与观察版本区分；变化/失效不静默沿用 |
| 知识库 | SQLite 检索台账；`.vela/lancedb/`；`.vela/embedding-spaces.json` | chunk ID、source、模型指纹、维度、索引 generation、stale 状态对应 |
| 项目文档与附件 | `.vela/documents/` 与 `.vela/documents/assets/` | 文档可重开、相对附件可解析；不误写正文表 |
| 导入进度与提交 | `import_runs`、effect/receipt、source identity 等相关表 | 重试幂等；来源身份和章节映射正确；中断不会重复提交 |
| 备份与恢复 | 授权目标的 `manifest.json` 和 `.vela/` 副本 | manifest 文件范围、SHA-256、SQLite 一致性、附件/向量恢复可用 |
| 全局模型/设置/提示词/Skill | 默认 `~/.vela/` 下 `config.json`、`models.json`、`recent-projects.json`、`prompts/`、`skills/` | 全局与项目覆盖关系；测试 home 隔离；损坏配置不被静默覆盖 |
| 主题/灵感/图片皮肤 | Electron profile 的 localStorage；全局 home 的 `skins/` | profile 重启保持；home/profile 范围符合 UI 说明；图片资源可读取 |

定位依据：`electron/database.ts`、`electron/vector-store.ts`、`electron/utils/config-utils.ts`、`electron/services/{world-map-image-store,manuscript-publisher,project-backup-service,skin-service}.ts`、`src/shared/project-documents.ts`。

每次写操作至少保存：功能 ID、runId、项目路径、会话身份、对象 ID、写前/写后数据摘要、存储绝对路径、成功/失败收据、独立回读结果。字节哈希用于稳定文件/冻结正文；SQLite 文件哈希会随内部状态变化，不能用来代替语义数据核对。

正常退出并确认 DB/WAL 状态后，用只读连接独立读取已提交数据，执行 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`。另对没有数据库外键约束的业务引用做断链检查。故障/崩溃用例应重新启动完成恢复后再检查，不能把未 checkpoint 的 WAL 数据当成未保存。

## 6. 八条跨功能场景

### E01：完整创作闭环

新建 A → 设置与角色 → 两卷蓝图 → 导入 v2 细纲 → 章节画布调整 → 绑定草稿 → 生成正文 → 保存 → 审稿 → 人工确认 → 修稿 → 差异确认 → 定稿 → 实体稿发布 → 单卷导出 → 退出重启。

检查蓝图/草稿/审稿/修订/定稿/导出全程身份；核对 prompt、正文哈希、SQLite 状态、分镜顺序、导出版本及重开界面。另验证下一章上下文中出现上一章确认结果。

### E02：外部资料到写作输入

只读外部合成资料 → 绑定/扫描 → 查看来源和变化 → 批准快照 → 规则/候选确认 → 装配章节上下文 → 写作输入 → 修改外部 fixture → 再扫描。

未经批准和过期来源不得静默进入 confirmed；来源与片段可追溯；只读扫描前后来源哈希不变。最后验证 B 无 A 的来源/规则/片段。

### E03：角色、世界、时间线与修炼

建角色 → 建两世界与地图 → 建势力/门户/规则 → 人物归属与当前位置 → 时间线事件 → 路径/轨迹 → 修炼体系 → 角色选级 → 保存重开 → 重命名/删除被引用对象。

逐项核对所有视图读同一稳定身份；不同世界的地图/规则/事件关联正确；删除策略给出影响，未处理引用不得显示为正常。

### E04：导入、编辑与导出

Markdown 多章选择 → 预览 → 取消一次 → 再选并确认 → 多草稿回读 → 编辑保存 → 分卷/版本导出 → 再读导出文件；另跑参考拆解和原稿恢复的阶段流程。

取消不产生草稿；新增 draft 不覆盖已有稿；导出选择版本正确；原文件字节不变；中断续跑不重复提交。

### E05：检索、重建与连续性

确认事实/定稿 → chunk 与索引 → 唯一标记检索 → 语义检索 → 来源定位 → 矛盾样本审计 → 保存 finding → 修改事实版本 → 标记过期 → 重建 → 重启检索。

同时核对 SQLite 台账和 LanceDB；用固定向量证明索引链路，再单独用真实 embedding 验证供应商链路。无 embedding 时 FTS 降级必须明示；不能用降级通过代替语义检索通过。

### E06：项目切换与迟到结果

A 开始写稿/保存/检索 → 延迟结果 → 切换 B → 返回 A 的结果；再测 A → B → A，重开 A 使用新 lease。

B 及新 A 会话不得被旧结果写入或刷新；明确报会话失效；保存失败时原编辑仍可恢复。同路径重新打开也视为新会话。

### E07：失败与恢复

依次注入数据库提交失败、实体稿落盘失败、索引失败、网络超时、流式截断、配置损坏、附件缺失和批准过程冲突。

每例核对提交边界：未提交不得成功提示；已经定稿提交但发布失败必须显示待发布；部分输出作为恢复候选；重试幂等；取消后没有迟到提交。故障注入只在测试实例或测试依赖中启用，不增加产品可用的越权后门。

### E08：重启、备份、恢复与迁移

完成 A 的全域 fixture → 正常退出 → 重启重开 → 备份 → 恢复到新目录 → 再次启动 → 数据与引用核对；再对 legacy 副本跑打开/迁移/再迁移。

核对语义快照、附件与冻结正文。当前备份实现以 `.vela/` 为范围，必须实测项目根目录实体稿等范围外文件的恢复/重新发布行为；不能未经验证称为完整项目备份。

## 7. 实施分层与已有证据的边界

| 层 | 使用方式 | 能证明什么 |
| --- | --- | --- |
| L0 功能登记 | 对照当前入口、契约、schema 和测试映射 | 范围没有无解释遗漏；不证明运行正确 |
| L1 现有单元/仓库/控制器回归 | 当前 Vitest Node 套件、真实临时 SQLite/文件 | 规则、事务、控制器行为、项目边界；不独立证明真实 UI 串联 |
| L2 浏览器功能测试 | 当前 `.browser.tsx` 套件 | 交互、保存错误展示、编辑保持；按实际后端标记 mock 或真实仓库 |
| L3 Electron 全链路 | 启动真实 main/preload/renderer，操作实际入口与原生对话框，退出重启 | 真实 IPC 注册、会话传播、磁盘持久化和联动；是本方案要补齐的核心 |
| L4 外部依赖与发布资格 | 隔离真实供应商、真实 embedding、MCP fixture、打包应用 | 服务/平台/原生模块实际可用；单独记录费用和运行条件 |
| L5 人工完整性评估 | 按约定流程实际创作，评估审稿解释与异常文案 | 文学质量、语义判断、流程是否方便；不以断言替代作者判断 |

当前可以复用的实际源码证据：

- `test/nav-backend-audit.test.ts` 有真实 SQLite 的多卷、多草稿、重开与 A/B 隔离测试，但调用 repository，不能独立算真实 UI 全链路。
- `electron/repositories/__tests__/world-workbench-persistence.test.ts` 有项目数据库世界关联/重开用例，可复用其数据核对方式。
- `src/components/editor/__tests__/BlueprintV2Editor.browser.tsx` 是组件 harness，使用内存 state，不能算编辑器到项目 SQLite 的验收。
- `test/cultivation-browser-backend.ts` 使用真实临时 SQLite 和仓库，但通过测试 IPC 分发及简化 schema，不能替代真实 preload/controller/项目 schema。
- `scripts/renderer-surface-e2e.mjs` 已使用 Playwright Electron，可参考隔离启动和重启取证；该脚本当前主要验证主题/皮肤，不代表全功能通过。
- `electron/services/__tests__/release-vector-smoke.test.ts` 使用受控固定 embedding，证明原生向量索引路径；真实 embedding 供应商需要另测。
- 蓝图 v2 以 `docs/blueprint-v2-contract.md` 的权威边界、无损与版本合同为验收标准。

以上仅为本轮源码勘察，未运行这些测试，也不沿用历史报告的通过结论。

L3 应优先复用已有 Electron 驱动。只允许替换网络/模型等外部依赖为确定性 fixture；真实 main、preload、controller、repository、项目 schema 和文件服务仍走产品路径。原生文件对话框至少安排真实操作验收；使用测试选择器替身的自动化场景必须披露边界，不冒充原生对话框已测。

## 8. 执行顺序与现有命令

先登记范围与隔离路径，再做静态检查、Node 回归、浏览器回归，最后做 Electron 场景与外部资格检查。SQLite 全局连接与 Node/Electron 原生 ABI 切换使这些阶段不能并发乱跑。

以下是当前已有命令，**本轮未执行**；尚未实现的全功能场景不伪造命令。

```powershell
# 工作树与环境记录
git rev-parse HEAD
git status --short
node --version
pnpm --version

# 现有检查及回归；分别保留退出码和完整结果
pnpm run typecheck
pnpm run lint
pnpm run check:i18n
pnpm test

# 使用前确认 Node 原生模块可用，浏览器和端口满足当前配置
pnpm run test:browser

# 独立 Node 原生脚本用例不假设包含在 Vitest 中
node --test scripts/lib/continuity-calibration.node-test.mjs scripts/lib/continuity-calibration-runner.node-test.mjs

# 真实 Electron 阶段需要 Electron ABI；之后再跑 Node 用例须切回
pnpm run rebuild:electron
pnpm run build
pnpm run test:renderer-surface:e2e
```

`pnpm test` 的 pretest 准备 Node 原生模块；浏览器脚本没有同样的 pretest。实际执行器须检查原生模块状态，并在 finally 中恢复执行前的环境。记录每阶段 ABI、浏览器版本、端口、退出码与耗时；测试失败后继续收集互不依赖的结果，依赖前置失败的场景标记阻塞。

附加插件单独在 `plugins/dsh-ai-novel-writer` 中执行 `pnpm test`（会先构建）和其资格检查。桌面默认 Vitest 配置在 `vite.config.ts` 中明确排除了 `plugins/`，所以桌面全量通过不能声称插件也通过。

发布安装/升级使用现有 `release:win:verify` 与相关 smoke 脚本，安排到独立发布阶段；不能为了创作链路检查直接升级用户的日常应用。

## 9. 结果格式与通过门槛

每个场景分别给出三个结论：链路、存储、完整性。不要合成一个模糊的“基本正常”。

| 状态 | 含义 |
| --- | --- |
| PASS | 当前基线实际执行，全部断言和回读证据满足 |
| FAIL | 可复现业务行为与验收标准不符 |
| BLOCKED | 缺少浏览器/原生环境/外部服务等条件，无法得出行为结论 |
| NOT_RUN | 尚未执行或本次不在执行范围 |
| MANUAL_PENDING | 自动化已覆盖机械链路，仍需文学/语义或实际原生 UI 评估 |

建议结构化记录：

```json
{
  "runId": "unique-run-id",
  "baseline": { "head": "full-sha", "dirtyDiffArtifact": "evidence/baseline.diff" },
  "caseId": "E01-v2-writing-finalization",
  "featureIds": ["F04", "F05", "F08", "F09", "F10", "F11", "F25"],
  "backend": "real-electron",
  "externalDependencies": "deterministic-provider-fixture",
  "chain": "NOT_RUN",
  "storage": "NOT_RUN",
  "completeness": "NOT_RUN",
  "storageEvidence": [],
  "reopenEvidence": [],
  "downstreamEvidence": [],
  "failure": null
}
```

每项失败保存最小复现步骤、期望/实际、断点层、影响对象、日志/截图、磁盘回读差异和修复后复验结果。按影响分级：数据丢失/串项目/越权为 P0；核心流程无法完成或错误读写为 P1；局部功能或恢复缺失为 P2；展示瑕疵为 P3。

通过门槛：

1. F01–F32 全部登记并拆出实际用例；所有未映射入口/处理器/存储都有明确处置。
2. 当前约定范围内，每个可持久化功能完成成功、失败、重开和下游读取核对；只读功能完成来源和权限核对。
3. E01–E08 的必要分支通过，P0/P1 为零；P2/P3 列明，不宣称全部完善。
4. 同时报告“登记功能覆盖”“场景执行覆盖”“真实存储回读覆盖”“Electron 全链路覆盖”“外部依赖覆盖”，分母包含 FAIL/BLOCKED/NOT_RUN；无需某维度时说明原因。
5. 必需场景的 BLOCKED/NOT_RUN 不得折算为 PASS。没有真实供应商证据时只能报告本地确定性链路结论。
6. 不通过加超时、放宽断言、删测试或只做关键词扫描获得通过。区分产品缺陷、用例隔离问题和环境限制。
