# AI 小说作家 2—8 阶段需求规格书

版本：v1.0-draft
适用范围：AI-Novel-Writer 桌面应用、项目数据库、知识库、逻辑审核引擎，以及 Codex/Antigravity 外部 Agent 接入。

## 1. 文档目的

本文件定义第一阶段和第二阶段基础能力完成后，后续第 2—8 阶段的产品需求、数据要求、接口边界、验收标准和阶段依赖。

这里的“第二阶段”包含两部分：

1. 已完成的故事资料管理基线；
2. 为连续性审核新增的事实账本、事件状态和影响分析增强项。

本文件不要求重做第一阶段的工作区中枢，也不要求重做已经通过验收的角色、世界观、蓝图、版本和审批能力。

## 2. 产品定位与基本原则

系统定位为小说的资料中枢、上下文装配器、连续性审核器和外部 Agent 工具层，不提供或托管 Codex、Antigravity 或其他模型的会员额度。

### 2.1 权威性原则

- SQLite 中处于 `approved/confirmed` 状态的结构化事实是正式依据。
- 原始 Markdown、正文和导入文件是可追溯来源。
- RAG 向量只负责召回证据，不负责决定事实真伪。
- AI 提取出的内容必须先进入候选状态，作者确认后才能成为正式事实。
- 无法确认权限、版本或来源时，默认失败关闭，不回退到旧的或未批准的内容。

### 2.2 修改原则

- AI 默认生成提案，不直接覆盖作者原文或正式设定。
- 所有写入都要经过版本校验、来源记录和审计日志。
- 作者可以锁定原文、接受部分修改、驳回提案或标记为“有意矛盾”。
- 外部 Agent 不得直接访问 SQLite、LanceDB 或项目文件；必须通过领域服务和 MCP 工具。

### 2.3 模型调用原则

- 规则检查在本地完成，不依赖模型 API。
- 深度语义审校由 Codex、Antigravity 或用户配置的其他模型完成。
- MCP 服务器只提供数据和安全动作，不调用用户的订阅账号 API。

## 3. 总体架构

```text
原始文件 / 作者正文
        ↓
SQLite 权威库
  事实、事件、状态、版本、审批
        ↓
文本切片与向量索引
  LanceDB + 全文索引
        ↓
上下文服务 / 逻辑审核服务
        ↓
应用界面或本地 MCP Server
        ↓
Codex / Antigravity
```

### 3.1 核心数据对象

- `Project`：小说项目。
- `SourceDocument`：原始设定、正文、细纲或参考文档。
- `Fact`：可判断真假的结构化事实。
- `Event`：剧情中发生的动作、变化或结果。
- `EntityState`：人物、物品、地点、组织在某个章节节点的状态。
- `StoryRule`：世界观、能力、时间或因果约束。
- `KnowledgeChunk`：用于全文或向量检索的文本片段。
- `AuditFinding`：一次审核发现的具体问题。
- `Proposal`：等待作者确认的事实或正文修改建议。

### 3.2 建议新增的数据库逻辑表

实际表名可按现有命名规范调整，但必须具备以下信息：

- `story_facts`：事实、状态、权威级别、来源和版本；
- `story_events`：事件时间、地点、参与者、前置条件和结果；
- `entity_state_snapshots`：章节结束时的人物、物品、地点和关系状态；
- `character_knowledge`：角色在章节节点已知的信息；
- `knowledge_chunks`：切片和来源映射；
- `embedding_records`：向量模型、索引版本和过期状态；
- `audit_runs`：审核任务范围、版本、规则集和执行状态；
- `audit_findings`：冲突位置、证据、严重程度和处理状态；
- `audit_waivers`：作者对有意矛盾或可接受风险的确认；
- `agent_sessions`：外部 Agent 调用的项目会话和权限边界；
- `mcp_audit_log`：外部工具调用、输入摘要、结果和写入回执。

## 4. 跨阶段非功能需求

### 4.1 数据安全

- 项目资料默认只保存在本机项目目录和本地数据库。
- MCP Server 默认只监听本地进程通信或本机回环地址。
- 不把 API Key、会员登录凭据或完整项目内容写入普通日志。
- 导出、删除和批量提交必须有明确的作者操作记录。

### 4.2 可追溯性

任何审核结论必须能够追溯到：项目版本、章节、文档、段落或字符范围、事实 ID、规则 ID和审核运行 ID。

### 4.3 性能

- 打开单章上下文时不得重新扫描全项目。
- 小范围修改优先增量更新事实、切片和向量。
- 全书审核采用可暂停、可恢复的批处理。
- 单章审核失败不应破坏已有正文、正式设定或索引。

### 4.4 版本一致性

- 审核使用的数据库快照、RAG 索引版本和正文版本必须记录在审核任务中。
- 发现版本过期时标记为 `stale`，不能静默使用旧结果。
- 并发修改采用乐观锁或 CAS；冲突时生成可解释的重新审核提示。

## 5. 第二阶段｜故事资料中心与事实账本增强

### 5.1 已完成基线

以下能力视为保留能力，不在本阶段重做：

- 人物、关系、世界观、蓝图和章节资料管理；
- 资料导入、来源登记和作者确认；
- 候选、确认、废止状态；
- SQLite 本地存储；
- 章节上下文所需的基础资料组织；
- 角色状态和故事线的已有展示能力。

### 5.2 新增需求

#### P2-FR-001 事实记录

系统必须允许将人物、地点、时间、能力、物品、关系和世界观规则表示为带来源的结构化事实。

#### P2-FR-002 事实来源

每条事实必须记录来源文档、章节、原文位置、提取方式、创建版本和确认人。

#### P2-FR-003 事件账本

系统必须记录事件的发生章节、时间、地点、参与者、前置条件、结果和来源片段。

#### P2-FR-004 状态快照

系统必须能生成并查询每章结束时的人物状态，包括位置、伤势、能力、关系、携带物品和已知信息。

#### P2-FR-005 候选确认

AI 提取的事实和状态只能进入候选区；作者确认后才可参与硬冲突审核。

#### P2-FR-006 影响分析

修改正式事实时，系统必须列出受影响的章节、事件、蓝图、伏笔和审核结果。

#### P2-FR-007 有意矛盾

作者可以将某条冲突标记为悬念、误导、不可靠叙事或其他有意设计，并填写理由。

### 5.3 验收标准

- 能从一章正文提取事实候选并显示原文位置。
- 未确认事实不会被当作正式规则。
- 能查看人物在任意章节节点的状态。
- 修改一条正式设定后能列出受影响章节。
- 事实、事件和状态都能回到具体来源。

## 6. 第三阶段｜RAG 与上下文服务

### 6.1 目标

在现有知识库和全文检索基础上，增加可过滤、可定位、可版本化的混合检索能力。

### 6.2 RAG 需求

#### P3-FR-001 文本切片

正文按场景、段落和语义边界切片；设定、人物卡和细纲按条目切片。切片必须保留相邻上下文标识。

#### P3-FR-002 向量元数据

每个向量至少关联项目 ID、文档 ID、章节 ID、切片 ID、事实 ID、版本 ID、来源类型、权威状态和原文位置。

#### P3-FR-003 混合检索

支持关键词、全文、向量和混合排序；专有名词优先保留精确匹配结果。

#### P3-FR-004 权威过滤

默认只将已批准内容作为正向事实；草稿、候选和废案必须明确标注并可按策略排除。

#### P3-FR-005 章节上下文接口

提供按章节装配上下文的服务，返回本章任务、相关设定、人物状态、前章承接、历史摘要和来源引用。

#### P3-FR-006 过期索引

正文或设定版本改变后，相关切片和向量标记为过期并进入增量重建队列。

#### P3-FR-007 无向量降级

没有本地 embedding 模型时仍必须能够使用 SQLite FTS 或关键词检索；降级状态必须向用户可见。

### 6.3 验收标准

- 输入“第31章、林越、左臂”能返回相关事实和原文位置。
- 搜索结果不会默认混入废案和未确认候选。
- 设定版本变化后，旧向量不会被静默当作当前事实。
- 所有返回内容都能显示来源章节和片段。
- RAG 失败时，章节上下文服务仍能返回可用的结构化数据库内容。

## 7. 第四阶段｜逻辑审核与连续性检查

### 7.1 目标

检查设定之间、章节之间、人物状态之间和剧情因果之间的冲突，并给出可验证的证据。

### 7.2 审核模式

- **章节预检**：保存或定稿前检查当前章节。
- **修改回归检查**：正文或设定修改后重新检查受影响范围。
- **卷级检查**：检查一卷内的时间线、人物线和伏笔推进。
- **全书批检**：可暂停、可恢复地检查全书。

### 7.3 确定性规则

#### P4-FR-001 时间与地点

检查时间倒流、到达时间不可能、地点连续性和行程约束。

#### P4-FR-002 生死与伤势

检查已死亡、失踪、重伤、昏迷或受限人物的异常登场和行动。

#### P4-FR-003 能力与代价

检查能力等级、使用条件、冷却、消耗、代价和世界规则。

#### P4-FR-004 人物知识

检查人物是否使用了尚未获得的信息。

#### P4-FR-005 物品与关系

检查物品持有权、交接记录、人物关系和称谓变化。

#### P4-FR-006 章节目标

检查正文是否完成逐章细纲中标记为必须完成的剧情任务。

### 7.4 语义审核

通过上下文服务向 Codex、Antigravity 或其他 Agent 提供证据，判断：

- 人物动机是否前后冲突；
- 剧情因果是否缺少必要前置；
- 世界观规则是否被绕过；
- 反转是否已有足够铺垫；
- 伏笔是否提前泄露或长期停滞；
- 人物性格、口吻和称呼是否漂移；
- 同一信息是否被重复解释。

### 7.5 审核结果

每个发现必须包含：

- 严重程度：错误、高风险、警告、信息；
- 规则编号或审核类型；
- 当前冲突位置；
- 对照的正式事实；
- 双方原文引用；
- 解释理由；
- 建议修复方式；
- 当前处理状态。

### 7.6 验收标准

- 能发现预置的时间、地点、生死、能力和知识边界冲突。
- 结果必须引用具体章节和原文位置。
- 作者可以驳回、修复或标记为有意矛盾。
- 未解决的硬冲突可以阻止定稿；普通警告不强制阻止。
- 审核结果不会直接覆盖正文或设定。

## 8. 第五阶段｜Codex 与 Antigravity MCP 接入

### 8.1 目标

让 Codex 和 Antigravity 在其原有订阅环境中直接调用小说项目的资料、RAG 和审核能力。

### 8.2 实现范围

- 新增本地 `AI-Novel-Writer MCP Server`；
- 优先使用本地 STDIO 传输；
- 提供结构化 JSON 输入和输出；
- 只暴露领域服务，不暴露数据库连接；
- 外部 Agent 的写入采用“提案—确认—提交”两步或三步流程；
- 保存调用日志、会话 ID、项目 ID、版本号和写入回执。

### 8.3 MCP 工具

只读工具：

```text
get_project_state
get_chapter_context
search_knowledge
get_character_state
get_story_timeline
get_open_threads
audit_chapter
get_audit_findings
```

写入提案工具：

```text
propose_fact_update
propose_event_update
propose_draft_update
propose_audit_waiver
```

确认提交工具：

```text
commit_approved_change
rebuild_knowledge_index
```

### 8.4 权限要求

- 只读工具默认可用。
- 提案工具必须返回 Proposal ID，不得直接写正式库。
- 提交工具必须校验作者确认、版本号和项目会话。
- Codex/Antigravity 断开或超时不能导致半提交状态。
- GUI 自动点击和模拟键盘不作为主要接入方式。

### 8.5 验收标准

- Codex 能读取指定章节上下文并获得来源引用。
- Antigravity 能调用同一 MCP Server。
- 外部 Agent 能执行章节审核并取得结构化结果。
- 外部 Agent 不能绕过审批直接修改正式事实。
- MCP 服务器重启后项目数据和审核记录不丢失。

## 9. 第六阶段｜章节创作工作台

### 9.1 目标

建立从逐章细纲、场景节拍到初稿、审核、修改和定稿的完整流程。正文可以在本软件、Codex 或 Antigravity 中完成。

### 9.2 功能需求

#### P6-FR-001 章节启动

选择章节后自动载入逐章目标、上下文、角色状态、必须完成事项和禁用约束。

#### P6-FR-002 场景拆分

支持场景、节拍、冲突、目标、转折和章末钩子编辑。

#### P6-FR-003 正文生成

支持整章初稿、续写选中文段、局部重写、扩写、压缩、对话重写和节奏调整。

#### P6-FR-004 原文锁定

作者锁定的正文不得被 Agent 静默修改。

#### P6-FR-005 版本管理

保存草稿、候选稿、修订稿和定稿，并支持差异比较和恢复。

#### P6-FR-006 定稿门禁

定稿前执行章节目标检查、逻辑审核和来源完整性检查。

#### P6-FR-007 新事实提取

从定稿正文提取新增事实候选，由作者确认后进入事实账本和 RAG 索引。

### 9.3 验收标准

- 一章可以完整走完“细纲—场景—正文—审核—修改—定稿”。
- 外部 Agent 生成的内容能回写为候选稿，而不是直接覆盖定稿。
- 定稿内容会进入后续章节上下文。
- 定稿后新增事实必须经过作者确认。

## 10. 第七阶段｜长篇叙事控制台

### 10.1 目标

面向几十万至两百万字连载，监控故事长期推进，而不仅是单章质量。

### 10.2 功能需求

- 卷、阶段和章节进度与字数；
- 主线、暗线、人物线推进曲线；
- 伏笔提出、推进、误导、揭晓和回收；
- 人物关系累计变化；
- 战斗、探索、日常、爽点、奇观和新信息密度；
- 连续多章无新信息或无新画面提醒；
- 配角离场时间和再登场提醒；
- 设定曝光频率和重复解释提醒；
- 卷级承诺、阶段目标和章末钩子检查；
- 下一章和下一卷的准备度。

### 10.3 验收标准

- 能按卷和主线查看剧情进度。
- 能查看未回收伏笔及最后推进章节。
- 能识别连续章节的低信息密度。
- 所有曲线指标都能回到章节或事件来源，而不是只显示模型评分。

## 11. 第八阶段｜全书修订与输出

### 11.1 目标

在全书或大卷完成后，提供可复核的整体修订、发布和迁移能力。

### 11.2 功能需求

- 重复情节、重复解释和相似段落检测；
- 注水章节和低推进章节识别；
- 人物弧光、关系变化和能力成长复盘；
- 伏笔回收总表；
- 卷级顺序调整建议；
- 前后文风、称谓和术语统一；
- 敏感词、平台风险和专业细节提示；
- 章节标题、章节编号和字数检查；
- Markdown、TXT、Word 等格式导出；
- 完整项目备份、恢复和迁移包。

### 11.3 验收标准

- 全书修订结果能够定位到具体章节和原文。
- 导出不会改变正式项目数据。
- 导出的文稿可以通过项目版本追溯回原始章节。
- 备份恢复后事实、向量索引状态和审核记录保持一致。

## 12. 阶段依赖与并行开发

```text
已完成的第一、二阶段
          ↓
事实账本 / 事件状态增强
          ↓
RAG 来源定位 ─────┐
          ↓       │
逻辑审核 ─────────┤
          ↓       │
MCP Server 骨架 ──┘
          ↓
章节创作工作台
          ↓
长篇叙事控制台
          ↓
全书修订与输出
```

可以并行：

- 事实账本和 MCP Server 的基础骨架；
- RAG 元数据和确定性审核规则；
- 章节工作台界面和审核结果界面。

不能提前依赖：

- 语义审核不能早于上下文和来源定位稳定；
- 外部 Agent 写入不能早于提案、审批和版本校验完成；
- 全书级指标不能早于事件和状态数据积累。

## 13. 建议里程碑

### M2：事实账本可用

事实、事件、人物状态、来源和候选确认可用。

### M3：RAG 可追溯

混合检索、向量元数据、版本过滤和原文定位可用。

### M4：章节审核可用

时间、地点、生死、能力、知识边界和章节目标检查可用。

### M5：外部 Agent 可调用

Codex 和 Antigravity 能通过 MCP 读取上下文、执行审核和提交作者确认后的变更。

### M6：章节创作闭环

细纲、正文、审核、修订、定稿和事实提取形成闭环。

### M7：长篇控制

卷级进度、伏笔、人物线和信息密度可视化。

### M8：全书输出

全书修订、导出、备份和迁移通过验收。

## 14. 明确不在本阶段范围内
